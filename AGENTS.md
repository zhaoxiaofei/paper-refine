This repository MUST satisfy these rules (i.e., constraints). These rules are binding on every code, command, stage, prompt, test and documentation change. A violation of any rule is a bug, not an acceptable trade-off; a change that needs an exception must amend this file first.

Rule 1. **Every session is exactly one role, and its role is the whole of its mandate.** A session reads the inputs its role is given, writes the one product its role owns, and neither performs another role’s work nor scores or ranks a product it wrote (rule 7):

   * REWRITE (when the round stages rewrites) — produces a complete alternative version of the base with the same documents, claims, data, and conclusions, reorganized and rewritten; it is not the correction surface — a source-hierarchy conflict is recorded under its problems-surfaced report for the operator’s round record, never resolved in the rewrite and never treated as a finding; the revision chain corrects only the findings it receives; it is not the reviewer, builds no finding ledger, edits no input, and its candidate is judged like any other;
   * REVIEW (round phase 1) — runs the adopted sweeps and judgment passes (M1–M36, J1–J5) and the discovery round (D0–D5) over the round’s base; when a prior round exists, it reconciles the prior round’s frozen findings and discovery list and, when the prior audit ran, reads its `prior_audit/UNRESOLVED.md` observations (rule 8); it writes its F-* and X-* rows (X-9xx reserved for the probe) into the round’s frozen finding list (the orchestrator appends the probe’s X-9xx rows after the probe’s cold pass and before the audit): identification only, nothing edited, nothing scored;
   * PROBE — reads the same corpus cold and unanchored (no checklist, no finding list, no review artifact) and files any defensible defect class under the recorded rules (rule 3) as X-9xx: identification only; its X-9xx rows join the reviewer’s in the frozen list for the auditor’s disposition, and its independence from the checklist is the point;
   * AUDIT — disposes every frozen finding (confirm, or drop with evidence; silence is not allowed) and attacks boilerplate closures and coverage gaps; it GENERATES NO NEW FINDINGS (no AU-* rows). Its product is the audit report: one disposition per frozen finding with the evidence that decides it. The same audit record carries an unresolved-observations section (`audit/UNRESOLVED.md`) for a defect it notices outside the frozen list — one line per observation, with its location and re-runnable evidence. The orchestrator carries that file into the next review as the read-only `prior_audit/UNRESOLVED.md` input; the next review alone may file an observation on the shared scale (rule 6), and an observation is not a finding, it never enters the frozen list the revisers act on, and no reviser acts on it. It edits no manuscript, review, or package, and its report is what the revisers act on. `--audit off` / `--no-audit` skips it: the frozen findings then reach the revisers unaudited.
   * REVISE (round phase 2) — applies the audited (or, when the review audit is skipped, the frozen) findings to the round’s base and writes its revised package (in a concern-scoped mode, inside the admitted concerns) plus its own change and manual report. In a concern-scoped mode, a source-hierarchy conflict outside the admitted concerns is recorded as `unable — outside admitted concerns` and is not edited; it is a named gap for a later unscoped revision. Before applying each finding it RE-VALIDATES that finding against the base and the source hierarchy and records the verdict (`confirmed` / `rejected`, with the reason) in its ledger; a rejected finding is carried as `unable — <reason>` and is not edited. It does not score or select, and the review and pristine copies it reads stay byte-identical;
   * REVISION AUDIT (after each revise arm, before integration/judge/round decision) — audits that arm’s revised version for the revision’s own classes and writes that arm’s BOUNDED-REPAIR PLAN (data): one row per defect it confirms in that revision, with the location, the wrong text or value, the correct value and the basis a different session can re-run, and the exact proposed repair. It GENERATES NO REVISED FILE and edits nothing (no manuscript, package, ledger or manual report); it does not re-review the submission and runs no discovery hunt over it. It does not score, rank or select (rule 7). `--revision-audit off` skips it: that arm’s revised version is then final for the arm, before integration when integration is staged;
   * BOUNDED REPAIR (only when that arm’s revision-audit plan is non-empty) — a REVISE-class session that applies the plan to that arm’s revised package and writes that arm’s revised version, final for the arm before integration. It RE-VALIDATES every planned repair against the revised package, the base and the source hierarchy before applying it (recording `confirmed` / `rejected` per row), applies only the confirmed rows, updates its ledger/CHANGELOG/MANUAL_STEPS and reports, and never re-reviews or re-audits. ONE pass only: a defect the post-repair verification still finds is recorded for the round’s decision, not repaired in a loop. That record may block certification (rule 10). It is not an input to the champion (rule 6). When the revision audit is skipped or the plan is empty, this role does not run and that arm’s revised version is final for the arm before integration;
   * INTEGRATE (when the round stages integration runs) — one run per pool member reworks its own copy with every other member as donor. It ports a fix only where the source hierarchy allows it and the finding is one the revisers may apply: confirmed in the audit report, or on the frozen list when the review audit was skipped. It reconciles every frozen X-* id in its difference ledger, a dropped id included; a dropped id is accounted for and is not applied. It authors no discovery hunt and judges nothing;
   * JUDGE — scores the anonymized comparison it received, never a finding list and never provenance (rule 4); it re-derives its own bounded discovery pass over every side and files its rows on the shared scale (rule 6), and the champion stays a pure function of the panel’s ledger, the digests, and which digest is the incumbent base (rule 6);
   * JOURNAL-MODE SESSIONS — the feedback and concerns sessions turn the human and pre-filtered LLM feedback into the complete enumerated concern ledger (and, where the mode replaces the general review, the finding list the single revision session follows). The concerns session reads that feedback as its object; it does not read the current-round general review’s or the probe’s findings. Where the mode replaces the general review, that round’s review object is the admitted concern ledger, not the full-package pass; the concerns review also reconciles the prior round’s frozen findings and discovery list and reads the prior audit’s `prior_audit/UNRESOLVED.md` observations under rule 8; every class the pre-filter dropped, and every class that ledger does not cover, is recorded as a named gap and is not a silent zero (rule 8). The response session writes the point-by-point response-to-reviewers letter — every concern id exactly once, quotes verbatim, only shipped targets cited; none of these edits a manuscript;
   * SCOPED REPAIR (after a rejected postcheck) — repairs only the rejected bookkeeping of a stage that already finished: it never creates a new deliverable; it corrects only the rejected bookkeeping file, never fabricates a missing record, and never touches the manuscript, the corpus, a package, or another stage’s deliverables.

The session order for a general round is REWRITE (each arm, when staged) together with REVIEW and PROBE (in parallel, when the probe is enabled; the rewrites and the probe depend only on the base, and the review depends on the base plus, when they exist, the prior round’s frozen findings and discovery list it reconciles and the prior audit’s `prior_audit/UNRESOLVED.md` observations it reads under rule 8) → AUDIT (optional) → REVISE (each arm) → REVISION AUDIT (per revise arm, optional) → BOUNDED REPAIR (per revise arm, only when that arm’s plan is non-empty) → each revise arm’s pre-integration revised version → INTEGRATE (when staged) → JUDGE → the round decision. A rewrite arm produces its candidate directly: it does not enter the revise/revision-audit/bounded-repair chain, and its candidate is judged with the other candidates (rule 1). The two auditors are optional by configuration (`--audit off` / `--no-audit` and `--revision-audit off`); when one is skipped its data is absent and the next step runs on unaudited input — the reviser on the frozen findings, that arm’s revised version as its pre-integration version — and the skip is recorded.

Where a session sees something outside its mandate, it records it for the role that owns it and never does that role’s work itself. The orchestrator is not a session role: it schedules these sessions, verifies their products, and computes the champion (rule 6).

Rule 2. **Facts are not a revision surface.** The operator’s source, the pristine copy, raw data, and external review feedback are read-only. The analysis code is not one of them — rule 9 makes it revision content. A read-only fact is never edited, dropped, or extended so that the manuscript looks right. It is never treated as the submission’s prose, never a word-count surface, and never a scored improvement. External review feedback is not a producer in the hierarchy below; it stays read-only, and a journal mode turns it into concerns rather than into a value that can win a disagreement. The manuscript is not required to match every source at once. When two sources disagree about a value, the higher producer wins and only an editable lower surface changes, highest to lowest: code, then raw data, then figures, then tables, then main text, then supplementary text. A read-only source never changes. Code outranks raw data, so a disagreement between them keeps the data byte-identical and brings the editable lower surfaces into agreement with the code. That is the agreement rule. It is not a second rule that the manuscript also match the raw data, and it is not a license to edit the data. A rewrite is a diversity arm, not the correction surface: it preserves the base’s conclusions and records the conflict under its problems-surfaced report for the operator’s round record; the revision chain corrects the findings it receives, not that report.

Rule 3. **No rule the venue did not state.** A venue is a recorded rule set. A journal name selects nothing. An article type is measured only against its own limits. If a limit, caption rule, section, or template requirement is absent, the pipeline counts and names the gap. It does not hard-code a journal, borrow another type’s numbers, copy exemplar prose, or let an agent invent a requirement. An invented rule is a defect in the pipeline, not a defect in the paper.

Rule 4. **Judgment is blind to provenance.** A judge sees the manuscript as an artifact, not as a product. It must not see which agent, arm, round, prompt, or prior session produced a version, and it must not see another session’s findings or discovery list. The panel refers to a version only by an opaque content token. External material needed to score the paper — raw data, code, and admitted reviewer concerns — may appear only as anonymized evidence, never as a label of which candidate is which.

Rule 5. **The thing that was scored is the thing that wins.** A candidate’s identity is its content digest. The champion pin, the next round’s base, and the published package are that digest’s bytes, not a later “cleaned up” cousin. Content-identical candidates are one candidate. A version that was not judged cannot win. Tracking, redlines, PDF renders, and post-hoc relabeling of the ledger are not allowed to move a pin, a score, or an input manifest.

Rule 6. **There is one ranking function, and it is pure.** Every scored defect lands in the same six tiers — correctness, preservation, completeness, consistency, writing, formatting — and the same four severities — **fatal, critical, major, minor**. A newly noticed phenomenon is mapped into that scale; it does not become a seventh ranked class. Given the panel’s own ledger (the score sheets and the defect rows it contains), the content digests, and which digest is the incumbent base, the champion is a pure function of those three inputs and of nothing else. The incumbent’s identity is the orchestrator’s input; it is not a label on the judge’s sheets (rule 4). The order key, applied to every candidate including the incumbent, is the panel’s defect census at the adaptive prefix — the census is counted per severity, tier, and source (peer, then own); the adaptive prefix is the shortest leading run of that ordered census at which the cleanest ranked version’s cumulative defect count reaches the operator’s recorded defect floor, or the whole census when no run reaches it; compared in the order fatal, then critical, then major, then minor, within a severity by the tier order named above (an earlier tier before a later one), and within a tier by source (peer, then own), a smaller count in the first position that differs being better, and the census not collapsed to one total, because a total would tie one fatal defect with one minor defect — then the panel’s median, mean, and IQR of its per-version scores (median and mean higher better, IQR lower better), then digest (lexicographic). That key orders the field. It does not by itself retire the incumbent: if the key’s leader is not the incumbent and that leader’s (median, mean, IQR) equals the incumbent’s exactly, the incumbent is kept, and this retention overrides the prefix and the digest. If the leader’s (median, mean, IQR) differs from the incumbent’s, the leader wins. If the field has no incumbent, the key stands, digest included. Content-identical candidates are one candidate (rule 5). Self-reported totals, conflict notes, and a defect audit may annotate that result. They may not replace its inputs.

Rule 7. **No role grades its own homework.** The session that writes a version does not score it. The audit neither scores nor selects, and the session that scores does not select the champion. The revision audit neither edits nor selects; the bounded repair is a revision role and never selects. A candidate changed by the bounded repair is a new artifact. The round has one judge. It runs after bounded repair and, when integration is staged, after integration, so the bytes it scores are the repaired bytes, or the integrated bytes when integration changes them. The pre-repair package is not scored and cannot win (rule 5). A repair of bookkeeping does not edit the manuscript. In a concern-scoped revision, changes stay inside the admitted concerns; an unscoped rewrite is a different mode, not a quiet upgrade of this one. The no-feedback path must stay the no-feedback path: adding a journal mode must not change what a root does when no journal mode is on.

Rule 8. **Every defect-seeking role has a non-zero probability of finding every real defect in the object it inspects — no rule may quietly set that probability to zero — and a defect that a finding-filing role finds is classified and evidenced the same way whichever of those roles found it.** The auditor does not file a new finding. A defect it notices outside the frozen list is an observation, with a location and re-runnable evidence and with no tier, until a later review files it on the shared scale (rule 1). For every defect-seeking role, a real defect inside the object it inspects is found by one run with a strictly positive probability; where that per-run probability is bounded below by a positive p and the runs are independent, the probability that n runs all miss it is at most (1 − p)^n, which tends to 0, so infinitely many runs on a package whose defects persist find it with probability 1; and any run that finds it, and whose product is a finding, classifies it the same way. Detection is probabilistic; the mandate, the evidence, and the classification are not:

   * the full defect-seeking passes — the probe (when enabled) and the round’s review, except a review that a journal mode has replaced — take the ENTIRE submission package as their object: every submitted document and file, every evidence area the operator assigned as input, the relationships between them, and the packaging itself. Where a journal mode replaces the general review, that round’s review object is the admitted concern ledger, and every class the ledger does not cover is a recorded gap, not a silent exclusion (rule 1). The other roles own the objects their design gives them — the audit the frozen findings (the review’s rows and, when the probe ran, the probe’s) plus the states it must re-derive, the integration arm the candidates it merges and the findings the revisers may apply (confirmed, or frozen when the review audit was skipped) together with the frozen X-* ids it must reconcile without re-applying a dropped id, the revision audit the revision’s own classes (read against the base, the revised package, the findings the revisers used — audited, or frozen when the review audit was skipped — and the revision ledger; not a re-review of the submission), the bounded repair the bounded-repair plan and the revised package it edits, the judge the comparison it received — and no rule, scan scope, prompt, or gate may narrow any role’s object to hide a class: no class of real defect — a class under the recorded rules, rule 3 — may be declared out of scope, exempt, or permanently unreviewable beyond the object this rule assigns that role. A class outside that object is not that role’s miss: it is inside another role’s object, recorded as a named gap, or — when no role and no gap can reach it — it is a defect in the PROMPTS (the next sentence); in every case it is not silently hidden. A class a prompt does not name is not thereby excluded; and a class a reviewer would raise that no role’s mandate can reach, and that no recorded gap names, is a defect in the PROMPTS, never a non-defect in the package;
   * no rule may make a defect invisible by construction: a scan that reaches only part of the package while instances of a class live outside its reach, a check whose reach is trimmed so the class falls out of it, or a filter that drops a class before any reviewer sees it and does not record that drop is zero-probability coverage for that class, and therefore a pipeline defect. A journal mode’s pre-filter is that defect when its exclusions are silent, and is not that defect when every excluded class is recorded as a named gap (rule 1). This forbids shrinking reach, never fixing precision: a check made accurate stops flagging non-defects without hiding any. Scoping a scan to its own legitimate surface — a formatting sweep over the submitted documents, a word count over the submission’s own prose, never the read-only evidence areas (rule 2) — is not such a narrowing while the classes that apply to the skipped area stay covered by the passes that read it, or are recorded as named gaps under rule 1;
   * a categorical gap a run cannot close (a tool missing in this environment, a rendering the sandbox cannot open, a dataset the operator did not supply) is never a silent cap: it is recorded together with the classes it leaves unexamined, so the next run samples them again. A gap that is stated keeps its probability; a gap that is hidden sets it to zero;
   * independence and variation are what make the probability accumulate: the probe and the judge’s own discovery pass read their object cold, without another current-round pipeline session’s findings or discovery list (rule 4’s blinding, applied to these passes as well as to the panel); the round’s review reads its object cold with respect to current-round sessions but reconciles the prior round’s frozen findings and discovery list; that prior-round reconciliation is a dependent input, not an independent run for the `(1 − p)^n` bound, so the bound applies to the independent probe/judge runs and to review runs not anchored on a prior list. The prior round’s frozen findings and discovery list, which the review must reconcile, are a reconciliation input from the base’s history, not another current-round session’s findings; external review feedback that a journal mode turns into the concern ledger is that review’s object, not another session’s findings; and successive sessions are expected to vary their entry points, orderings, and enumerations rather than repeat one route. A role that adjudicates or acts on another session’s rows (the audit; the revision and integration arms) receives them as rows to dispose of, fix, or reconcile, never as a substitute for examining what its own mandate covers. Sampling breadth is a correctness requirement, never a stylistic preference;
   * what is FOUND by a finding-filing role travels: its tier and severity are the same whichever of those roles found it (rule 6’s scale), and its evidence is re-runnable by a different session — a location, a verbatim quote, or a computation another role can repeat; any one of the three is enough. A finding no other role can verify is not yet a finding. An audit observation does not travel as a scored defect. It travels as a location and re-runnable evidence through the read-only `prior_audit/UNRESOLVED.md` input to the next review, which is the role that may file it (rule 1);
   * deterministic agreement between roles is required of the scale and the evidence, NEVER of a single session’s detection list — detection lists may differ between sessions, and that variation is the sampling the probability rests on. Two asymmetries keep this consistent with the roles’ design: the auditor’s agreement is a DISPOSITION — uphold a row, or drop it with evidence — so a drop is a legitimate outcome, not a disagreement to be suppressed; and a judge’s object is the comparison it received, so a defect outside that comparison is out of its object rather than a miss by the judge (it is another role’s object, a named gap, or a defect in the PROMPTS when no role and no gap can reach it). Silence from a role whose object did not contain the defect is neither agreement nor contradiction;
   * the guarantee stays probabilistic: a session that runs, examines, and reports nothing has not proven the package clean, and no output may present a completed review — probe, review, audit or panel — as an exhaustiveness proof. Only the stronger claim, that a class has probability zero, is forbidden outright.

Rule 9. **Nothing that ships points at what does not ship.** A submitted document may refer only to content the submission itself carries. A path into an area or file the submission leaves out — the analysis code when it does not ship, the author’s own `README*.md`/`README*.txt` files, the raw data, the review feedback, the pipeline’s own bookkeeping and scratch — is a reference the reader can never resolve, so it is a defect in the submitted file, never a nuance of packaging. This does not flatten the areas into one kind: the raw data and the review feedback stay read-only inputs under rule 2, never revised and never submitted; the analysis code is revision content — revised and evaluated like any other file — and is submitted only when the operator asks for it; the author’s README files are carried by the corpus and never submitted. The rule binds one direction only — the submitted side is aligned with what actually ships, and an excluded area is never widened, edited, or extended so that a dangling reference appears to resolve.

Rule 10. **Output is not certification.** That a `final_clean_version_<root name>/` is always written does not mean the decision passed. Certified means the panel was complete, the champion re-derives from the panel’s ledger, the digests, and which digest is the incumbent base (rule 6), the evidence is unchanged, and the enabled gates are clean. A skipped integrity check is reported as skipped. Provisional and blocked results stay labeled and are never presented as a signed answer.

Rule 11. **A root runs a frozen copy, never the maintained checkout.** `setup` must copy every file the running project executes or reads by path into the `--root` tree before the root is used. This includes, but is not limited to: the driver(s), their ordered parts, companion modules and adapters (the formatter and its parts, redline and Qwen adapters), venue profiles, schemas, prompt/config assets and any other file whose content can change a stage's behavior. The copy must be self-contained: after `setup`, modifying, updating, moving or deleting files in the maintained checkout must not change what that root executes, reads, validates, prompts with or scores with. Reading a repository file from a root at run time instead of using the root's frozen copy is a bug; add the asset to the setup copy and the module/asset manifest. A feature that adds a runtime file without freezing it into new roots violates this rule.

Last rule. **On a contradiction, the earlier text wins.** If two rules contradict each other, the rule that appears first in this file — the lower number — prevails, and the later rule is read as narrowed to what the earlier one allows. If two sentences contradict each other — in one rule or in two — the sentence that appears first prevails, and the later sentence is read as narrowed to what the earlier one allows. A contradiction remains a defect in this file, to be repaired by editing; precedence is the default reading until the repair is made.
